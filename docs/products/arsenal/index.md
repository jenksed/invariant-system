# Arsenal

Arsenal captures engineering judgment that is worth learning once and reusing: repository reconnaissance, ambiguity resolution, diagnosis, review, verification, continuation, and other recurring methods.

It is not the execution engine. It does not gain repository authority because one of its methods recommends a change.

## What exists now

The current tree contains:

- a machine-backed asset/catalog model;
- capability contracts and validation;
- deterministic compilation/distribution work for Agent Skills;
- Repository Truth as a concrete portable distribution path;
- engineering methods and workflows across software, research, review, and verification;
- evaluation and qualification machinery under Bench;
- trust, knowledge, observability, and qualification tests invoked by the root Arsenal gate.

The generated `CATALOG.md` is a library view, not the best introduction. Start with the product README and the specific methods you need.

## Boundary

Arsenal owns intelligence, methods, evaluation, qualification, and learning. It must not become Kiln's runtime execution authority or grant mutation permission.

That distinction lets Arsenal evolve its intelligence quickly without turning every method update into an execution-policy change.

## Bench relationship

Bench is not another product directory. It is the evaluation/qualification evidence domain inside Arsenal at `products/arsenal/evaluation/`.

## Current limitation

Arsenal's deeper capability architecture continues to evolve. Existing assets, compiler paths, and evaluation machinery are real; future capability-system prose must not be flattened into a claim that every planned lifecycle/routing feature is already complete.

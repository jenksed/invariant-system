# Loadout Product Boundary

## Default product experience

The user should think “I want to do X,” not “Which product should I use?”

Loadout presents the Goal, selected Capability, progress, approvals, evidence, blockers, history, and Result. Kiln remains the canonical source for runtime facts displayed inside that experience.

## Two system views

### Innovation

- Arsenal → qualified useful method → Loadout Capability.
- Arsenal → qualified necessary invariant → Kiln mechanism.
- Loadout and Kiln return reviewed observations to Arsenal.

### Use

- User Goal → Loadout Capability → Work Envelope → Kiln Run → Run Result Envelope → Loadout Result view.

These views are complementary. Loadout and Kiln are sibling products in innovation ownership, while Kiln normally operates beneath Loadout in the user journey.

## Precision boundaries

- **Connector:** Loadout-owned discovery/configuration for an external system.
- **Effect driver:** Kiln-owned execution surface for an authorized mutation or observable operation.
- **Result:** Loadout-owned presentation of the attempt.
- **Runtime record:** Kiln-owned canonical facts and evidence.
- **Acceptance readiness:** Kiln-owned evaluation of declared executable gates.
- **Acceptance:** Human or explicitly authorized workflow decision.

Kiln can establish that evidence was obtained and bound to state. It cannot establish that a model genuinely understood the material or that the product is universally correct.
